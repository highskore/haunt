# haunt-core API (Phase 2)

The Swift app talks to the core through one UniFFI object, `HauntCore` (`ffi/src/lib.rs`). The core owns the sidebar view-model: Swift renders `SidebarSnapshot` verbatim and doesn't format text or decide state. The events adapters send are specified in [agent-events.md](agent-events.md).

## Object

```
object HauntCore {
  constructor(config_dir: string)                 // normally ~/.haunt
  fn start() -> Result<(), CoreError>             // binds sock and ctl, opens decisions.jsonl; a second call is a no-op
  fn register_surface(cwd: string) -> Result<SurfaceEnv, CoreError>   // Invalid past 512 surfaces
  fn unregister_surface(surface_id: string)
  fn set_surface_info(surface_id: string, title: string, cwd: string, git_branch: Option<string>)   // title and git_branch are ignored
  fn select_surface(surface_id: string)           // marks Row.selected
  fn on_osc_notification(surface_id: string, title: string, body: string)
  fn snapshot() -> SidebarSnapshot
  fn snapshot_if_newer(version: u64) -> Option<SidebarSnapshot>   // nil while snapshot.version is still `version`
  fn set_listener(listener: CoreListener)
  fn answer_permission(surface_id: string, request_key: u64, allow: bool) -> Option<bytes>
  fn has_unresolved(surface_id: string) -> bool   // a verified prompt may be on screen; only verified events clear it (see Nonce gating)
  fn on_user_input(surface_id: string)           // every keyDown routed to that surface
  fn decisions(query: string, limit: u32) -> sequence<Decision>     // newest first
  fn decisions_in(query: string, surface_id: Option<string>, limit: u32) -> sequence<Decision>   // one tab's, filtered before the limit
  fn allow_suggestions() -> sequence<AllowSuggestion>              // plugin proposals that pass every check
  fn accept_allow_suggestion(project: string, command: string) -> Result<(), CoreError>
  fn dismiss_allow_suggestion(project: string, command: string)
  fn review_turn(surface_id: string) -> Option<ReviewTurn>          // the latest turn, for the review screen (docs/review.md)
}

callback interface CoreListener { fn changed() }

record SurfaceEnv { surface_id: string, nonce: string, socket_path: string }
error  CoreError { Insecure { reason }, Io { reason }, Invalid { reason } }

record SidebarSnapshot { groups: sequence<SidebarGroup>, color_style: ColorStyle }
record SidebarGroup { id: string, label: string, rows: sequence<Row> }   // id: needs-you, running, idle, pinned, tabs, section:<id>
record Row {
  surface_id: string, kind: RowKind, name: string, meta: string, task: string, status_text: string,
  needs_you: bool, progress: Option<Progress>, subagents: sequence<Subrow>, selected: bool,
  pending: Option<PendingRequest>, color: Option<TabColor>, decoration: Option<Decoration>
}
record Decoration { label: Option<string>, label_tone: Tone, suffix: Option<string>, suffix_tone: Tone, scroll: bool,
                    bar_permille: Option<u16>, spark: Option<Spark> }   // a plugin's, see rows below
record Spark { points: sequence<u8>, tone: Tone }
enum   Tone { Dim, Text, Needs, Kbd }
enum   TabColor { Red, Orange, Yellow, Green, Blue, Purple, Gray }
enum   ColorStyle { Dot, Tint }
record PendingRequest { key: u64, tool: string, preview: string, suspicious: bool }
enum   RowKind { Shell, Claude, Codex }     // an agent without a kind of its own is Claude
record Progress { done: u64, total: u64 }
record Subrow { label: string, meta: string }

record Decision { at_ms: u64, surface_id: string, tool: string, preview: string, command: Option<string>, cwd: Option<string>, outcome: Outcome, agent: Agent }
enum   Agent { Claude, Codex, Other { id: string } }   // "claude", "codex" or the id in decisions.jsonl; absent is Claude
enum   Outcome { AllowedInHaunt, DeniedInHaunt, AllowedByPlugin { plugin_id: string }, DeniedByPlugin { plugin_id: string }, AnsweredInTerminal, Superseded, RefusedPlugin { plugin_id: string, reason: Refusal } }
enum   Refusal { NoTab, NoRequest, NotOnScreen, InTerminal, TerminalOnly, NoKeys }   // refusalText(reason:) is the host's own text
record AllowSuggestion { project: string, command: string, rule: string, approvals: u32, plugin_id: string }

record ReviewTurn {
  agent: Agent, number: u32, prompt: Option<string>, cwd: Option<string>, started_ms: Option<u64>, finished_ms: Option<u64>, failed: bool,
  head_at_start: Option<string>, tool_count: u32, edit_count: u32, tasks: sequence<TurnTask>,
  commands: sequence<TurnCommand>, files: sequence<string>, subagents: sequence<TurnSubagent>
}
record TurnTask { subject: string, status: string }
record TurnCommand { command: string, outcome: CommandOutcome }
enum   CommandOutcome { Running, Passed, Failed, Unknown }
record TurnSubagent { label: string, tool_count: Option<u64>, duration_ms: Option<u64> }
```

`select_surface` is an addition to the contract as first agreed, because `Row.selected` needs a source. `SidebarGroup` was renamed from `Group` because a Swift `struct Group` would shadow SwiftUI's `Group`.

In Swift, the generated `Progress` struct shadows `Foundation.Progress` inside the module. Write `Foundation.Progress` if you need the other one.

## Using it

1. Create one `HauntCore(configDir: "~/.haunt" expanded)`, call `setListener`, then `start()`. If `start` throws, show the reason and keep running: the OSC fallback still works, but only for status.
2. For each new surface, call `try registerSurface(cwd:)` and put these in the pty environment. It throws `Invalid` once 512 surfaces are registered; open the tab without the env then (hooks fall back to status-only OSC).

   | variable | value |
   |---|---|
   | `HAUNT` | `1` |
   | `HAUNT_SURFACE_ID` | `env.surfaceId` |
   | `HAUNT_HOOK_NONCE` | `env.nonce` (128-bit random, hex) |
   | `HAUNT_SOCK` | `env.socketPath` |

3. On `PWD` and title changes, call `setSurfaceInfo`, from any thread, with `gitBranch: nil`: the core reads the branch itself. On tab selection, call `selectSurface`. When a tab closes, call `unregisterSurface`.
4. On `GHOSTTY_ACTION_DESKTOP_NOTIFICATION` with title `haunt://cli-agent` or `warp://cli-agent`, call `onOscNotification`. The core ignores other titles, so the UI can pass every notification through and still show the non-agent ones itself.
5. `changed()` fires on whatever thread made the change. That is often the socket thread. Hop to the main actor, then call `snapshot()`. It is never called while the core holds its lock, so calling back into the core is safe. It fires once per burst: after a call, further changes don't call it again until the next `snapshot()` or `snapshotIfNewer` that returns one, so a UI that stops taking snapshots stops being called.
6. Allow/Deny: a row with `pending` has a nonce-verified request. If `pending.suspicious` is set, show the preview with a warning and no Allow/Deny: the request is terminal-only (see Nonce gating below: hidden characters, a tool that may touch more than it shows, or another request possibly still on screen), and `answerPermission` returns `nil` for it. It can clear while the key stays the same, once the request is the only one left. Keep `pending.key` with whatever offers the answer (the button, a notification's `userInfo`) and pass it back: `answerPermission(surfaceId, requestKey, allow)` returns the asking agent's keys, which the app sends as keystrokes (Ghostty's `text:` binding action), never through `ghostty_surface_text`, which pastes and which a prompt ignores. A keystroke answers whatever prompt is up, so it must only go out for the live request the gate just checked: the app calls `answerPermission` (or `gatePluginRequest`) and presses the key in the same main-thread turn, so nothing can change between the check and the press. The keys are in `core/answer-keys.json`, which both the core's and the app's tests check: `"1"` (allow) or `"\u{1b}"` (deny) for Claude Code, `"y"` or `"\u{1b}"` for Codex (see [agent-events.md](agent-events.md#agent-ids)). An agent haunt has no keys for gets no `pending` at all. For Claude Code, `1` picks Claude Code's first option, "Yes", wherever the highlight is, where Enter would pick the highlighted one ("Yes, and don't ask again" or "No" if the highlight moved). In a prompt that defaults to No, Claude Code hides the indexes and ignores digits, so `1` does nothing there rather than answering No. It returns them only while that key is still the surface's live request, and consumes the request, so a second call, or a key from a prompt that has since changed, returns `nil`. If it returns `nil`, write nothing.

### UI must call

- `onUserInput(surfaceId)` on every keyDown routed to a surface (before or as it goes to the pty). Once the user types at the terminal, the prompt may already be answered and the tool running until `PostToolUse` arrives, so a late Allow (`1`) or Deny (Esc) from haunt would be typed into the running session. The call retires the surface's live request: `pending` disappears, `answerPermission` returns `nil`, and the request is logged when its outcome is known (`AnsweredInTerminal` if the matching tool runs, else `Superseded`). The macOS app makes its surfaces `HauntSurfaceView` (`macos/Sources/HauntSurfaceView.swift`), a subclass of the vendored `Ghostty.SurfaceView`. libghostty has no single write choke point the app can hook (clipboard reads also serve OSC 52), so the subclass calls it before `super` on each user write path: `keyDown`, the three paste actions, `insertText` (IME, Character Viewer, dictation), middle-click `otherMouseDown`, `performDragOperation`, `readSelection` (Services), and whenever a paste confirmation resolves. Ghostty's own bindings reach the surface through `keyDown` as well, menu shortcuts never do, and the vendored sources stay unpatched. Mouse clicks and scrolls that a TUI's mouse mode reports, and key-release events, are not counted: a click to focus the terminal shouldn't drop the request. The same paste paths (the paste actions, middle click, drag and drop, Services) also check the text first: one with an escape, another control or a hidden character gets Haunt's own confirmation sheet before Ghostty sees it. Ghostty 1.4 asks only about line breaks and `ESC[201~` (unsafe even in a bracketed paste), and its paste encoding turns ESC and the other controls into spaces, so the user would never see what the text held. A paste that passes is handed to `ghostty_surface_paste_text` as the text that was checked, so Ghostty's own protection still applies and the clipboard is never read twice. A confirmed paste goes out through `ghostty_surface_text`, which encodes it the same way. Because Haunt hands over the text itself, an app that turns on kitty paste events gets a plain paste, not Ghostty's MIME-listing event. Middle click is Haunt's: Ghostty's `middle-click-action` is always `ignore`, and Haunt pastes only when the app isn't capturing the mouse and the user hasn't set `[ghostty] middle-click-action = ignore`. Any other clipboard access Ghostty asks about (an OSC 52 read under `clipboard-read = ask`) is denied and logged; writes, allowed by default, never ask. Ghostty's own paste keybinds (⌘V, ⇧⌘V, the Paste key) are always unbound, and the `[ghostty]` keys that let libghostty paste by itself are refused (see README, Configure), so these paths are the only ones.
- `try registerSurface(cwd:)`: it throws now (past 512 surfaces), so `CoreAPI.registerSurface` must be `throws` and its callers need `try`.
- `gatePluginRequest(request:)` for every `.ptyAnswer` and `.ptyType` from `HauntPlugins.takeRequests()`, writing only the bytes it returns (see Plugins).

Elapsed times in subrow meta are computed when `snapshot()` runs. `snapshot.nextTickMs` is the time until one of them next reads differently (a running subagent's clock), or `nil` when nothing on screen depends on the clock: schedule one `snapshot()` then instead of a steady timer. `snapshot.version` goes up with every change, so `snapshotIfNewer(version)` can skip a redraw that changes nothing; a clock tick still needs `snapshot()`.

## Decision log

Every verified permission request is recorded once, when it ends, with its outcome:

| outcome | when |
|---|---|
| `AllowedInHaunt` / `DeniedInHaunt` | `answer_permission` with the live key |
| `AllowedByPlugin` / `DeniedByPlugin` | a plugin's `.ptyAnswer` through `gate_plugin_request`; in `decisions.jsonl` it is `{"allowed_by_plugin":{"plugin_id":…}}` |
| `RefusedPlugin` | a plugin's `.ptyAnswer` the gate refused for the request on screen (`terminal_only`, `no_keys`); the request stays live. Not an end: the request gets its own outcome later. Left out of the 0.4 `decisions.query`, which has no case for it |
| `AnsweredInTerminal` | a verified `tool_ran`/`tool_done`/`tool_failed` matched it, so it was allowed at the terminal prompt |
| `Superseded` | anything else ended it: a newer prompt, leaving `needs you` (including a denial typed in the terminal, which then shows up as the next prompt or stop), or the surface closing |

Requests only exist for verified events, so unverified events never add an entry; they can only end a verified request, which is then logged as `Superseded`. Entries live in memory (the last 10,000) and in `<config_dir>/decisions.jsonl`, one JSON object per line, appended. `start` opens it with `O_NOFOLLOW`, refuses a symlink or a file of another uid, keeps it 0600, and loads the existing lines. Loading is strict: a line with an unknown field or outcome, an empty surface id or tool, or a `command` that isn't a Bash command whose `preview` shows exactly that command is skipped. Before `start` the log is memory-only.

`decisions(query, limit)` returns them newest first; `query` is a case-insensitive substring of tool, preview, cwd, outcome (`allowed_in_haunt`, …), surface id, agent id (`codex`) or plugin id, and empty matches all. `decisions_in` keeps only one surface's, before the limit, so a tab filter never misses its older decisions behind other tabs' newer ones. The ⌘K `log` mode is not built in: it is the first-party plugin `dev.haunt.decision-log` (`~/code/haunt-plugins/haunt-decision-log`), which reads the same records through the `decisions` import (see Plugins). Lines reach `decisions.jsonl` after the state lock is released, in order; a line that fails to write stays in memory and is counted in `haunt dump`.

## Allowlist suggestions

Nothing is allowed by default. The core keeps the safety primitives: it counts approvals, holds the proposals and is the only thing that writes a rule. When to offer a rule is a plugin's call: the first-party `dev.haunt.allowlist` (`~/code/haunt-plugins/haunt-allowlist`) proposes one after 3 identical approvals. The core never suggests anything on its own.

A plugin with `allowlist_suggest` reads the counts (`allowlist.approvals(min-count)`) and calls `allowlist.propose(project, command)`. That only records a pending suggestion and fires `changed()`; it writes no file. `allow_suggestions()` lists the proposals that still pass every check, with the exact rule `Bash(<command>)`, the current count and the proposing `plugin_id`, most recently approved first. Every proposal is checked when it is made, whenever suggestions are listed, and again on accept:

- It needs at least one counted approval of exactly that command in exactly that project. Only Claude Code approvals count, because Claude Code is the one agent that reads `.claude/settings.local.json`, and only clicks in haunt (`AllowedInHaunt`). `AllowedByPlugin` and `AnsweredInTerminal` never count; see the nonce limit below. A plugin can't propose a command you never approved.
- Counting uses `Decision.command`, the command exactly as the hook sent it (`ToolCall.raw_command`), not the shown `preview`. An approval counts only if the two are equal, so a command with invisible characters, tabs or newlines (which the preview shows as markers) never counts, and a rule can't allow a variant of what was approved. Log lines without `command` (written before it existed) don't count.
- Wildcards are never suggested: a command containing `*`, `(` or `)`, anything outside printable ASCII, leading or trailing spaces, or over 1024 bytes can't be proposed.
- The project (the hook cwd) must be absolute with no `.` or `..` components, equal byte for byte to its canonical path (so no symlink anywhere in it, and no trailing or doubled slash), and a directory owned by the current uid (`Invalid` or `Insecure` if it fails).
- A rule the user accepted or dismissed in this run can't be proposed again. At most 256 proposals are kept.

`accept_allow_suggestion(project, command)` only accepts a current suggestion (`Invalid` otherwise) and adds the rule to `<project>/.claude/settings.local.json` under `permissions.allow`, keeping every other key and their order (the file is re-indented). A file that isn't a JSON object, or a non-object `permissions` or non-array `allow`, is an `Invalid` error and is never overwritten. It refuses (`Insecure`) a symlinked `.claude` or settings file and never follows one: the directory is opened with `O_NOFOLLOW`, and the new content goes to a temp file (`O_EXCL | O_NOFOLLOW`) in it that is renamed over the old one. The file keeps its mode, or gets 0600 if new. Accepted and dismissed suggestions are not offered again in this run. Neither that memory nor the proposals are persisted yet, so after a restart the plugin proposes again, and a dismissed rule comes back.

## Snapshot format (mockup layout 06, grouped flat)

Groups, in order: `NEEDS YOU`, `RUNNING`, `IDLE`. Done, failed and shell rows go in `IDLE`. Empty groups are left out. The `IDLE` label is empty only when the sidebar holds nothing but shells; once any agent row is listed, `IDLE` keeps its label even over shells alone, so they never read as part of the group above. Within a group, the most recent status change comes first. Ties keep tab (registration) order.

| field | shell | agent (Claude, Codex) |
|---|---|---|
| `name` | last path component of the cwd (`~` for home) | same, of the agent cwd |
| `meta` | `~cwd · <shell>`, e.g. `~/code/vibes · zsh` (the basename of `$SHELL`) | `branch · task`; the agent cwd stands in for a missing branch |
| `task` | empty | the `task` half of `meta` on its own, empty when there is none |

The agent cwd is the latest verified hook event's `cwd`, falling back to the surface cwd from `setSurfaceInfo`. A Claude launched as the surface's command never changes the shell's `PWD`, so the hook is the only place its cwd shows up. The core reads every branch itself, from `.git/HEAD` above the cwd: the surface cwd's on each `set_surface_info`, and the agent cwd's on every verified event, so a checkout inside the session shows up. The lookups run outside the state lock and are cached per surface by cwd and HEAD (inode, size, mtime), so an unchanged HEAD costs one `lstat`. `title` and `git_branch` are ignored; they stay in the signature so the app's call needs no change.
| `status_text` | empty | `needs you`, `3/5` (running with progress), empty (running without progress), `done`, `failed`, empty (idle) |
| `progress` | none | `done/total` of the main agent's tasks, else of its latest TodoWrite |
| `subagents` | none | while running or needing you (a turn that stopped with background subagents still running counts as running, grouped under RUNNING, until the last one stops): `label` = `Explore · trace hooks`, `meta` = `2/4 · 1m12s` or `14 tools · 48s` |

The task part of `meta`:

- needs you: `Approve: git push?` for a verified Bash request, `Approve: Edit /w/a.rs?` for other tools, and `Waiting for you` when the request isn't verified
- running: the subject of the latest in-progress task, else the prompt (one line, at most 120 characters)
- done: `Done in 4m` (`45s`, `4m`, `1h5m`)
- failed: `Failed`

A surface becomes an agent row with its first agent event and stays one until it is unregistered. Its kind follows the `agent` of the latest verified event (`Claude` until one arrives). Phase 1 hooks send no session-end event.

### Arrangement (`core/src/arrange.rs`)

A plugin granted `sidebar` (the first-party one is `dev.haunt.tabs-plus`) can push an arrangement: pinned tabs, named sections, a manual order, a flat list, and colours. The core merges it over its own grouping on every `snapshot()`:

1. `NEEDS YOU` (`needs-you`) first: every row that needs you, in the core's order, whatever the arrangement says. When a pinned or sectioned row stops needing you, it goes back to its place.
2. `PINNED` (`pinned`): the pinned rows, in the plugin's order.
3. The plugin's sections (`section:<id>`), before or after step 4 as the arrangement's `placement` says. A row listed in more than one place goes to the first: pinned, then sections in order.
4. `RUNNING` (`running`) and `IDLE` (`idle`) with the rest, or one `TABS` group (`tabs`) when `flat` is set. Rows the plugin ranked in `order` come first, in that order, and the rest follow in the core's order. One global order means a tab that leaves RUNNING and comes back keeps its place. A group of shells only still has no label.

Every row shows exactly once. Unknown and repeated surface ids are ignored, and empty groups are left out. A section title is 1 to 32 ASCII letters, digits, spaces and basic punctuation (`-_.,:;!?'&()/+#`), so no lookalike letters from other scripts; it is single-spaced and uppercased like the core's labels. Its letters and digits may not spell `NEEDS YOU`, `RUNNING`, `IDLE`, `PINNED` or `TABS`, so `N-E-E-D-S YOU` is refused too. Section ids are lowercase letters, digits and `-`. At most 32 sections and 1024 ids per list; `sidebar.arrange` refuses anything else.

The first plugin to arrange owns the sidebar until it calls `clear` or goes away; others get an error. An arrangement belongs to the loaded instance that set it. It is dropped when that plugin is disabled (a trap or timeout), reloaded or removed, and the snapshot applies only an arrangement whose instance is still loaded with `sidebar`. `Row.color` is set only for rows the plugin coloured. `SidebarSnapshot.color_style` says how to draw it: `Dot`, a small dot beside the name, or `Tint`, a faint background. Without an arrangement every row has no colour and the style is `Dot`.

The colours are names, so the app picks shades that sit in the black-and-white design. `design/tokens.json` is generated from the mockups, so they belong in Swift (or a hand-kept token file), not there. A starting point: dot at full value, tint at about 12% over `color.sidebar.bg`.

|---|---|
| Red | `#b07a7a` |
| Orange | `#b08f72` |
| Yellow | `#ada27a` |
| Green | `#84a083` |
| Blue | `#7f93ad` |

## Transport and security

**Socket** (`core/src/intake.rs`, owned by `HauntCore`): `<config_dir>/sock`. The debug/CLI socket `<config_dir>/ctl` follows the same directory, socket and peer-uid rules (below).

- The directory is created with mode 0700. `start` refuses (`CoreError::Insecure`) a directory that is a symlink or is owned by another uid. If it has group or other bits, it is ours, so they are removed. The socket is chmod 0600, and its owner and mode are checked after `bind`.
- A leftover socket of ours is replaced. `start` refuses anything else at that path, a socket owned by another uid, and a socket that still accepts connections (`CoreError::Io`: another haunt is running). It also refuses a path longer than `sun_path` allows.
- Every connection's peer uid (`getpeereid`) must equal ours. At most 32 connections are open at once. Each line must arrive whole within 2 s of the previous one, and a connection is closed after 10 s in total, so a peer trickling bytes can't hold the slots and silence the hooks. A connection with replies still unsent isn't read from, and one whose single read queues over 1 MiB of replies is closed once they are sent. Out of file descriptors, accepting pauses for 100 ms rather than spinning.
- Messages are newline-delimited JSON of at most 64 KB. A longer line is discarded, and the stream continues with the next line.
- Each line is one v1 event ([agent-events.md](agent-events.md)) with `surface_id`. Lines for a surface that isn't registered are dropped before rate limiting, so random ids cost nothing. Each surface is rate-limited to 50 events/s with a burst of 200, separately for verified and unverified lines, so a flood of forged lines for a known surface id can't drop the real ones; extra lines are dropped and counted. Lines no surface id can be read from (over the limit, not UTF-8) share one such budget. The branch lookup at a hook's cwd and the plugin event tap run on their own threads, so a hung mount or a slow plugin never holds up the socket; each queues at most 1024 jobs and drops the rest. No branch is looked up on a filesystem the mount table (read without asking any filesystem) marks non-local or automounted, and that answer is cached per cwd. The branch cache's lock is never held during a lookup, so the UI's own lookups never wait on another surface's.

**Nonce gating** (`core/src/session.rs`): an event is *verified* only if it came over the socket and its `nonce` matches that surface's nonce, compared in constant time. Unverified events (wrong or missing nonce, or any OSC 777 event) may change status and progress, but can never create an answerable request. The rules:

- Only a verified `permission_seen` creates a request, and only if it isn't `truncated` and carries a command or file path. Otherwise the row shows "Waiting for you" and the user answers in the terminal.
- Leaving `needs you` for any reason, verified or not, drops the request.
- Each entry into `needs you`, and each `permission_seen`, starts a new generation. A request can be answered only in the generation that created it. So an unverified event that puts the row back into `needs you` (a forged stop and then a forged `permission_prompt`, say) can never revive an old request. A forged unverified `permission_seen` retires the real one, which costs the user the button. A forged verified one is another matter: see What the nonce does not protect against.
- `answer_permission` needs the surface to be in `needs you` with a live request at that moment whose key is the one passed in, not `suspicious` and not retired by `on_user_input`, and consumes it.
- `has_unresolved(surfaceId)` is true while the surface has a verified request, pending (even one typing took over) or ended without its call being seen (see One request at a time, below). Unverified events never clear it, unlike a row's `needs_you`, so anything else that types into the surface, such as the review screen's send-back, must refuse while it is true.
- Only a tool whose one command or file path is all it may touch is answerable: `Bash` by its `command`, and `Edit`, `MultiEdit`, `Write`, `NotebookEdit` and `Read` by their `file_path`. Every other tool (`apply_patch`, which can write many files, MCP tools, a future tool) is `suspicious`: shown, answered only in the terminal. The command or path is kept byte for byte as the hook sent it, and matched and written to allow rules unnormalised. An input holding U+FFFD is `suspicious` too: some hop replaced bytes it couldn't decode, so what runs may not be what is shown.
- One request at a time. A request that ended without its call being seen may still be on screen: one a newer `permission_seen` or a move to another call retired (Codex queues the approvals of parallel calls and shows the oldest first), and one answered from Haunt (the keys may not have landed on its prompt). While any such request is outstanding, the live one is terminal-only, so an Allow can't land on the wrong prompt. Only a verified `tool_ran`, `tool_done` or `tool_failed` with the same `tool_use_id`, tool name and thread (`agent_id`) clears one; a request without an id can't be told apart from a lookalike call, so it stays outstanding even after a call with its input runs. Otherwise a request clears only when the user has typed into the surface since it was shown and a verified `prompt_submit` then arrives, or the surface closes. `stop` and `stop_failure` never clear one, and neither does a `prompt_submit` with no typing before it, since a hook can send those while a prompt is up. Past 16 outstanding requests, every request stays terminal-only until such a typed new turn, so a flood can't push a real one out. A denial (typed into Codex, or sent from Haunt) leaves its request outstanding, so the rest of that turn is answered in the terminal.
- A `tool_use_id` is taken from a verified `tool_start` on the same thread with the same tool and exact input, and only when exactly one such start is pending; a start lends its id once and leaves when its call ends. Otherwise the request stays id-less.

A request resolves when a verified `tool_ran`, `tool_done` or `tool_failed` matches it. The match is on `tool_use_id` when both sides have one (the id is taken from the matching `tool_start`), otherwise on tool name plus exact command or file path. An event with `truncated: true` never matches. Any change out of `needs you`, or an answer, also clears it. For an agent other than Claude Code (Codex has no failure hook), a verified tool event from the same thread that isn't the pending call also ends it as `Superseded` (see [agent-events.md](agent-events.md#agent-ids)).

**Invisible characters**: the hook sends `tool_input` strings over the socket unmodified (JSON escapes keep them on one line). Every other decoded string has control characters and Unicode format characters (General_Category Cf: bidi overrides U+202A–202E and U+2066–2069, zero-widths U+200B–200F, U+2060, U+FEFF, soft hyphen, tags and so on) and Default_Ignorable_Code_Point characters (Hangul fillers U+115F/1160, U+3164, U+FFA0, variation selectors, U+034F and the rest) removed, and other whitespace turned into a space. `core/hidden-chars.json` lists both sets; the core and the app are tested against it.

A request keeps its command or file path exactly as sent. Its `preview` hides nothing: a newline shows as `⏎`, a tab as `⇥`, and any other control, Cf, non-space whitespace (line and paragraph separators included) or Default_Ignorable_Code_Point character (Hangul fillers, variation selectors, U+034F and the rest) as `\u{…}`, so `ls #\nrm -rf ~/x` shows as `ls #⏎rm -rf ~/x` and can't pass for a comment. A request with any such character is `suspicious` too: `answer_permission` refuses it (it stays live until the terminal answers) and it is never suggested for the allowlist. Matching a request to its `tool_ran` uses the exact input too.

**What the nonce does not protect against**: `HAUNT_HOOK_NONCE` is in the pty environment, so every process the session starts inherits it, including the commands Claude's tools run. Code running inside the session can therefore read it and forge verified events for its own surface: a fake `permission_seen` (which retires the real request and shows its own preview), a fake `tool_ran` (which logs `AnsweredInTerminal`), a fake cwd. Such a process can also make Haunt answer the wrong prompt: it reads what is pending from the screen, sends a verified `tool_ran` for it and then a `permission_seen` for a command of its choice, and if the user clicks Allow on that preview the keys go to whichever prompt is really up. The gates above narrow this (an id-less request never clears without typing, and a turn end never clears one), but don't close it: an Allow is only as trustworthy as the session that asked for it. Verification separates the hooks from other local programs and from text printed into the pty (OSC), not from the session's own tools. That is why `AnsweredInTerminal` never counts toward allowlist suggestions, only a click in haunt does, and why a plugin's `${cwd}` grant never widens to `$HOME` or the haunt dir.

**OSC 777 fallback**: `haunt://cli-agent` and `warp://cli-agent` bodies go through the same parser, but they count for status only. The haunt hook sends a stripped-down status body there (no nonce, at most 250 bytes).

## Plugins (`HauntPlugins`, feature `plugins`)

Installed with `haunt plugin install <path>` (cli/), which shows the capabilities, asks y/N (`--yes` for scripts) and pins sha256 of the wasm and manifest in `~/.haunt/plugins.lock`. A plugin whose files no longer match is not loaded until `haunt plugin approve <id>`. A capability in the pinned grant that this haunt doesn't know (a newer haunt wrote it) is dropped, never granted, and the rest loads.

`haunt plugin new <name> [--dir <path>] [--id <id>]` scaffolds a plugin repo from `cli/template/`, a snapshot of the `haunt-plugin-template` repo embedded in the binary, with `wit/haunt-plugin.wit` from this checkout. The id defaults to `dev.haunt.<name>` and must pass the same reverse-DNS rule as the manifest; it refuses a non-empty folder and runs `git init`. When the template repo changes, copy it over `cli/template/` (without `wit/`); `cli/tests/plugin.rs` builds and installs the scaffold.

Each call runs under a 50 ms CPU budget and 64 MB of memory; a trap or timeout disables that plugin until the next load.

Events reach plugins on the thread that delivered them (usually the socket thread), after the core has released its lock. A plugin call holds the plugins' lock and may then take the core's, through `decisions` or `allowlist`; the core never calls a plugin while holding its own. `propose` and `arrange` fire `changed()` from inside a plugin call, so the listener must hop to the main actor and not call `HauntPlugins` synchronously.

**Event details** (`event_details`, red consent line "reads the commands, file paths and prompts your agents use; these can contain secrets"): without it `command`, `file-path` and the prompt and plan in `summary` are none, since they can carry tokens, `.env` paths and pasted keys. `request-key` goes only to plugins granted `pty_write`.

**Event fields**: `surface` is the tab's id. `tool`, `command` and `file-path` come from the tool call (or the `file_edited` event); `command`, `file-path` and `cwd` keep what was sent with hidden characters spelled out as the preview shows them (`⏎`, `⇥`, `\u{…}`), so a plugin sees what the user would. `summary` (a task's subject or status, the tool name, the prompt, the plan), `session-id`, `agent-id`, `tool` and `task-id` are plain: whitespace becomes a space and hidden characters are removed. Commands, paths, cwds and summaries are cut to 1024 characters (`EVENT_TEXT`), ids and tool names to 256. `request-key` is set only on a verified `permission_seen` whose request is live and from an agent haunt knows the keys of; it is the key `pty.answer` takes. A terminal-only request (suspicious, or with an earlier prompt possibly still on screen) carries it too, so a plugin can follow it, but `pty.answer` on it writes nothing.

**Verified events**: `agent-event.verified` is true when the event came over the socket with the surface's nonce (see Nonce gating). An unverified one (OSC 777, wrong or no nonce) can be forged by anything that prints into the terminal, so treat its fields as untrusted. A plugin granted `pty_write`, `pty_type`, `allowlist_suggest` or `decisions_read` gets verified events only. Only a verified event's `cwd` widens a `${cwd}` grant.

**Plugin settings** (`core/src/plugin_settings.rs`): `init` and `on-settings-changed` get one JSON object. It holds each `[settings]` key from the manifest with its `default` (a manifest whose entry has no `default` doesn't install), and over those the user's `[plugins."<id>"]` table from config.toml. A user value is kept only if the manifest declares its key and it has the same TOML type as the default (a list for a list, a string for a string). An undeclared or mistyped key is dropped and reported through `settingsProblems`. A plugin's JSON may be at most 256 KB (`MAX_SETTINGS`); over that it keeps its previous settings (the defaults at load) and the problem says so. The plugin checks the values themselves. The app passes the text to `load` and again to `setConfig` whenever config.toml changes. `setConfig` does nothing unless the `[plugins]` tables changed, and then calls only plugins whose JSON changed. Before `on-settings-changed` the host drops that plugin's palette commands (not its modes), so it must register the commands its settings call for again; one removed from the settings leaves the palette at once. A config.toml the `toml` crate can't parse applies nothing at load, so plugins start on their defaults, and on a later change it keeps every plugin's previous settings; `settingsProblems` says it doesn't parse. A plugin that a trap disabled isn't loaded again by a settings change; the problems tell the user to restart Haunt.

**API version**: `haunt:plugin@0.5.0`; manifests say `api = "0.5"`. Older plugins no longer install or load; rebuild them against the 0.5 WIT.

- 0.2 added the `decisions` and `allowlist` imports (below), and `at-ms`, `mark` and `surface` on `palette-item`, plus the `mark` enum.
- 0.3 added `verified` on `agent-event`, the `sidebar` import (below), and two exports every plugin implements. `row-menu(surface) -> list<menu-item>` builds context-menu entries; a chosen entry calls `on-action(id, surface)`. `on-row-moved(surface, group, before)` is called only for plugins granted `sidebar`.
- 0.4 added the `theme` import, the `typing` import with its `pty_type` capability (both below), and the `on-theme-changed()` export every plugin implements.
- 0.5 added `surface`, `tool`, `command`, `file-path`, `task-id` and `request-key` on `agent-event` (see Event fields); `on-event` returns nothing, and rows are decorated through `rows` instead. It also added the `rows` (`decorate`), `timer` (`timer`), `panel` (`panel`) and `clock` imports, and the `on-tick(now-ms)` export every plugin implements.

**palette** (always linked): `mode(word, title)` and `command(id, title, default-key)` register entries, at most 64 per plugin. An empty id, or one with a hidden character (`event::is_hidden`: controls, bidi and zero-width characters, whitespace but the space), is refused and logged; a title loses its hidden characters and is cut to 80 characters, for every plugin. A plugin can't remove an entry: only the host clearing its commands before `on-settings-changed` (see Plugin settings) does. Backlog for the WIT: a `palette.remove` or `set-commands` import.

**theme** (always linked): `name()` and `tokens()` return the app's current theme: a name ("default" is black and white) and its colour tokens, each a dotted lowercase name such as `color.hairline` and a `#rrggbb` or `#rrggbbaa` value. They are read only and need no capability, since colours tell a plugin nothing about your work. Until the app calls `setTheme` they are the colours in `design/tokens.json`; after a switch every plugin gets `on-theme-changed()`.

**sidebar** (`sidebar`):

- `rows()` returns the rows in the core's order with surface id, name, kind (`shell`, `claude`, `codex`), state group and selection. It includes no meta, task, prompt or command text.
- `arrange(arrangement)` sets this plugin's arrangement, merged as described under Arrangement, and `clear()` gives the sidebar back.
- Surface ids last as long as their tab and are new after a restart, so per-tab state keyed by them starts over with every launch.

**rows** (`decorate`, consent line "can add a label, a bar or a sparkline to your tabs' rows"): `decorate(surface, some(decoration))` sets this plugin's decoration of an open tab's row and `decorate(surface, none)` removes it; `clear-all()` removes all of them. The core keeps one per row and plugin instance, as `Row.decoration` (`core/src/decorate.rs`), and the row shows one: the first plugin in config.toml's `[layout] row_labels` that has a decoration there, else the one loaded first (lockfile order, which is install order). `PluginConfig` reads `row_labels` (at most 64 names; anything but a list of strings is ignored and reported) and passes it to `CoreHandle::set_row_labels`. The other decorations' labels, or their suffixes, go in `Row.other_labels` for the row's tooltip, except on a row that needs you. A plugin that is disabled, reloaded or removed loses its decorations, and a closed tab's go with it. Every string goes through `plugins::plain` (whitespace to a space, hidden characters removed): `label` at most 24 characters (`LABEL_MAX`), `suffix` 64 (`SUFFIX_MAX`, 160 when it scrolls); one with nothing visible left becomes none. A `label` in the `text` tone is refused, since it is too close to the needs-you white, and so is one that contains a status word or phrase anywhere (`says_status`): every fixed text the sidebar shows for a status (`layout::STATUS_TEXTS`: needs you, running, idle, waiting for you, approve, done, failed), "waiting" alone, allow and deny. The label is compared after NFKC, lowercasing and dropping combining marks, then each character's TR39 confusable skeleton (`unicode-security`), lowercased, with lookalikes folded (0→o, 1, i and | → l, 5→s, rn→m, vv→w); any character that wasn't ASCII still matches any letter, but a match needs at least one letter that is equal, so emoji alone spell nothing. The sidebar's own phrases and "waiting" are refused anywhere in the label's letters and digits, whatever stands between them (`ok-done-ok`, `[x]done[x]`, and also `idler` and `abandoned`). Allow and deny count only as a word of their own, words splitting at whitespace and the sidebar's separators (`·`, `:`, `?`) with ASCII punctuation inside a word dropped and a run of one-letter words joined, or at the start or end of the label at a break (`Al·low ok`, but not `allowlist ok`). So `d0ne`, `ldle`, `don℮`, `⍳dle`, `d○ne`, `D∨NE`, `✓ done`, `Allo\u{353}w` and `done 3/4` are refused, and `CI 7/9`, `spec 11/18`, `3 edits` and `allowlist ok` are not; the spark may still be `text`. `bar` is clamped to 0..1 and kept as `bar_permille`; NaN or an infinity is refused. A `spark` has at most 32 points (`SPARK_MAX`), each 0 (bottom) to 255 (top). On a row that needs you or has a pending request, `State::snapshot` drops the label, spark and suffix, so nothing a plugin writes can hide or imitate haunt's status (the app drops them again); only the bar stays. The app draws the spark (56×14) or else the label (mono, at the status size) in the status slot, the suffix after the meta line behind " · " in its tone, and the bar in place of the task bar. Tones: `dim` the meta colour, `text` the primary, `warn` an orange of its own (`Tok.App.pluginWarn`) for failures such as red CI. Haunt's needs-you colour and a key-cap style aren't offered. With `scroll` the suffix may be 160 characters (`TICKER_MAX`); the app doesn't animate it yet.

**timer** (`timer`, consent line "can run on its own every 15 seconds or more, not only when an agent event arrives"): `every(seconds)` asks for `on-tick(now-ms)` every 15 (`TICK_MIN_SECS`) to 86400 seconds, replacing any earlier interval; `stop()` ends it. `attach` starts a `haunt-tick` thread only when some enabled plugin holds `timer`; it looks once a second, skips that second if the set is busy (so a tick can come late, by as long as the set stays busy), ticks the plugins that are due (each call under the usual budget) and fires the listener when requests are waiting, as an event would. `now-ms` is Unix ms to the second, like the WASI wall clock. The thread ends when the `PluginSet` is dropped or no timer plugin is left enabled.

**panel** (`panel`, red consent line "can show its own panels: a sheet, a side pane, a small card or a window"): `show(id, placement, title, nodes)` shows panel `id`, or replaces the one this plugin showed under that id; `close(id)` closes it. The app draws it natively from a flat list of nodes, each naming an earlier `vstack` or `hstack` as its parent (none: the panel itself): text, row (label, sub line, right-hand value), button, divider, grid (cells 0 to 1, shaded from the background to the text colour in five steps, below 0 empty, `marked` cells outlined in the plugin warn orange) and canvas (dots, rects, lines and labels on a fixed `width` × `height`). Tones are `text`, `dim`, `faint` and `warn`; a dot or rect may be `warn`. Nothing in a panel uses Haunt's needs-you colour. `plugin_panel::build` checks it in the host and refuses: an id that isn't 1 to 64 of letters, digits, `-`, `_`, `.`; more than 512 nodes (`MAX_NODES`), 8 levels or 4096 shapes; more than 16 pulsing dots (`MAX_PULSES`); a parent that isn't an earlier stack; a grid whose cells aren't rows × columns, over 4096 cells, a cell size outside 2 to 64, a drawn size over 2048 points either way, or a marked cell outside it; a canvas over 2048 points either way; a button without an action; any number that isn't finite. Shades are clamped to 0..1, canvas coordinates to a canvas-sized margin, and every string goes through `plugins::plain` cut to 256. A plugin has at most 4 panels open (`MAX_PANELS`) and 4 shows a second (`SHOWS_PER_SEC`). A sheet takes the keyboard, so a show is one only while the plugin handles something the user just did (a palette command, its key, a panel button; `HostState::user_call`); otherwise it comes up as a card. One sheet is up at a time across all plugins (`CoreHandle::claim_sheet`; a show while another plugin's is up errs), and the app shows a plugin sheet as a card while any sheet, Haunt's own included, is already attached. For 10 s after the user closes one of a plugin's sheets (`SHEET_COOLDOWN`) it can't show another, and a second close within a minute (`SHEET_STRIKES`) ends its sheets for the session. Every show gets a new `generation`. Each show queues `HostRequest.showPanel(pluginId, pluginName, panel)`, a close `closePanel(pluginId, id)`; a disabled plugin's panels are closed the same way. There is one right pane: a show there from another plugin or id closes the old one (a `closePanel` is queued for it and its plugin gets no `on-action`), and only the owner's close, or the owner showing that id somewhere else, clears it. A drain lists requests plugin by plugin rather than in call order, so when the owner shows in the right pane again in the same drain, another plugin's show there in that drain is dropped (its panel closes without an `on-action`). Placements: `sheet` over the main window (Esc closes it), `right` a pane beside the terminal, 320 pt at first; the user drags the grip on its left edge to set it from 280 to 480 pt, and the app keeps that width per plugin in state.json (`right_pane_widths`), `card` a small floating card at the window's top right, `window` its own window titled "From <plugin name>". Every placement has a header the host draws and the plugin can't style: "From <plugin name>" and a close button; the plugin's title goes under it. Content taller than 80% of the screen scrolls. No show takes focus, and Return is never bound to a plugin's button, `primary` included. The app's `PluginPanels` calls `HauntPlugins.panelAction(pluginId:panelId:generation:action:)` for a button, which reaches the plugin as `on-action(action, "panel:<id>")`, and with an empty action when the user closes the panel (its ×, Esc, or the window's close button). The host refuses an action that isn't a button of that show, an older show's action or close, and a close of a panel that isn't open. The app closes every panel when the plugins are replaced.

**clock** (`timer`): `local-offset-min()` is the user's UTC offset in minutes now, from `localtime_r`; WASI clocks are UTC. It tells a plugin the time zone, nothing else.

**decisions** (`decisions_read`): `query(text, limit)` returns the same records as `HauntCore.decisions`, at most 1000, without the raw `command` (the preview shows it with nothing hidden). It is read only: nothing a plugin can call adds, changes or removes a decision.

**allowlist** (`allowlist_suggest`): `approvals(min-count)` returns the counted approvals (Claude Code, clicked in haunt, the raw command equal to its preview) per project and exact command, newest first. The host raises `min-count` to at least 2 (`APPROVALS_MIN`), so a one-off approval, such as an `export TOKEN=…`, never reaches a plugin. `propose(project, command)` adds a pending suggestion; it errors if the proposal fails a check (see Allowlist suggestions). No import writes a settings file, and none can accept a suggestion. Only `HauntCore.acceptAllowSuggestion` does, after the user accepts it in the UI.

An ungranted import is absent: a component that imports it fails to link at install and at load.

**Bundled plugins**: `macos/make-app.sh --plugins <names|all>` builds the plugins named (each the repo `haunt-plugins/haunt-<name>`, id `dev.haunt.<name>`: today `allowlist`, `commands`, `decision-log`, `tabs-plus`; none by default) plus the repos in `HAUNT_FIRST_PARTY_PLUGINS`, and puts each in `haunt.app/Contents/Resources/plugins/<id>/` as `haunt-plugin.toml` and `plugin.wasm`, inside the signature. The setup sheet and Settings show each one's `name` and `description` from its manifest (`name` is one line of at most 64 characters and `description` an optional one of at most 160; `license` and `homepage` are capped at 64 and 256, none may hold control, format, bidi or zero-width characters, and `version` is 1-32 of letters, digits, `.`, `+` and `-`). The CLI also escapes such characters in any manifest text it prints. Nothing installs them on its own:

- `haunt setup --plugins <names>` (or the setup sheet, or Settings) installs one after showing its capabilities. The FFI's `installBundledPlugin` does it without a prompt, only in the fixtures build (the `fixtures` feature). It goes through `Store::install_bundled_plugin`, pinned with `source = "bundled"`. `Store::preview_bundled_plugin` gives the plan without writing anything (`Preview::Unchanged` only when the copy on disk still matches the lockfile; otherwise installing again rewrites it), and the install goes ahead only if it asks for exactly the capabilities the preview showed. `--remove-plugins` removes it; a copy from another source is left to `haunt plugin remove`.
- On launch, `Store::install_bundled` only updates the bundled plugins already installed. When the app ships a different build of one, it is updated in place, unless it asks for a capability the pinned one wasn't granted. Then the new files go on disk unpinned, the plugin stops loading ("does not match the lockfile"), and `haunt plugin approve <id>` shows the full prompt.
- A copy installed from another source is never replaced. Removing a bundled plugin adds its id to the lockfile's `removed_bundled`, so launches never touch it again, until `haunt setup --plugins` installs it again.

**Theme plugins** (data only, `plugin_pack.rs`): a manifest with no `entry` runs no code. Its only capability is `theme = true` (consent line: "adds a theme: colours, fonts and window effects. Its fonts can change how text, including the terminal, is drawn. Runs no code"), and it names its files in `[contributes.theme]`:

```toml
[capabilities]
theme = true

[contributes.theme]
id = "glass"                      # what `theme = "glass"` in config.toml names; not "bw"
file = "theme.toml"               # the theme file, as in docs/themes.md
fonts = ["fonts/Exo2.ttf"]        # .ttf, .otf or .ttc
licenses = ["OFL.txt"]            # required with fonts
```

- Paths are relative and plain (no `..`, no absolute path). A file that is a symlink, or sits in a folder that leads out of the plugin's folder, is refused.
- Caps: 256 KB for the theme file and each licence, 8 MB a font, 24 MB in all.
- `install` copies exactly the manifest and those files into `plugins/<id>/` and pins one digest over them (`sha256_files` in the lockfile, with `sha256_wasm` empty). `load_all` re-hashes them, so a changed file stops the theme loading until `haunt plugin approve <id>`.
- Two plugins with the same theme id: the second one is a load error.
- The app registers a theme's fonts for its own process only (`CTFontManager`, `.process` scope), and only while that theme or one it extends is on screen. A theme in `~/.haunt/themes` with the same id wins over the plugin's.
- Themes installed while the app runs show up after a relaunch.

**fs grants**: `${cwd}` in an `fs_read`/`fs_write` glob means the agent's project folder: the root of the git work tree the tab is in, once the plugin has seen a verified event from that tab, and again on each one (at most 16 folders, `MAX_CWDS`). `FsScope::project_folder` resolves it from the folder the tab was opened in (`Surface.opened_in`, which the app passes to `register_surface`), never from the cwd the shell reports (`Surface.cwd`, OSC 7) or the cwd an event names: an OSC 7 can't add a root, so a tab steered into a sibling repository still gets only the one it was opened in. A new tab inherits the focused tab's cwd, so only a repository root counts: the walk up from the canonical cwd stops below `$HOME`, and a `.git` file's gitdir must be inside the `.git` folder of a work tree that could itself be a root (a worktree's or submodule's), or be a folder that could be a root; a worktree's `commondir` must pass the same test (`gitdir_allowed`). Both files are read as git reads them, dropping only trailing `\n` and `\r`, and one with another line or with leading or trailing whitespace is refused (`git_pointer`). The root must be strictly inside `$HOME`, not under a dot-folder or `~/Library`, neither inside the haunt dir nor containing it, and not itself `~/Documents`, `~/Desktop`, `~/Downloads`, `~/Pictures`, `~/Movies`, `~/Music` or `~/Library/Mobile Documents` (`TCC_ROOTS`; a project inside one is fine). A tab at `~` or in a folder outside any repository gets no `${cwd}`, so its reads and writes are refused; if `$HOME` can't be resolved `${cwd}` expands to nothing. No path inside the haunt dir is ever readable, writable or listable, whatever the globs say. From 0.5 every `fs_read` and `fs_write` glob must start with `${cwd}/` (`FS_PREFIX`): a manifest with an absolute one doesn't install, and the host drops any other from the lockfile's grant and lists each it dropped in the load errors. Both consent lines are red; reading's is ("can read files matching <the agent's project folder>/…, which can contain secrets"). The path is canonicalised and matched, then opened one component at a time with `O_NOFOLLOW`, so a symlink can't lead outside the grant. `read` returns at most 4 MB (`FILE_CAP`) and refuses anything but a regular file; `list` returns the matching names, sorted, and errs past 4096 of them (`LIST_CAP`) or 65536 entries looked at.

Accepted risks of the `${cwd}` and `exec` roots:
- A new tab (⌘T) starts in the selected tab's live cwd, which its shell reports (OSC 7), and that becomes the new tab's `opened_in`. So an agent that steers its shell into another repository under `$HOME` can make that repository the next tab's root. It takes the user opening a tab, and the new shell visibly starts there; "an OSC 7 can't add a root" holds for tabs already open.
- `gitdir_allowed` lets a `.git` file point into another root-eligible repository's `.git` (worktrees and submodules live there). A repository whose `.git` file points at a neighbour's `.git` has `exec` read the neighbour's history (`git-log`, `git-status`) under its own root. Both repositories have to be ones `${cwd}` could grant anyway.

**pty writes** (`pty_write`): a plugin can only call `pty.answer(surface, allow, request-id: u64)`, where `request-id` is the `key` of that surface's pending request. There is no free-form text under `pty_write`: a plugin typing arbitrary text with ESC or `\r` could drive the session. Typing is the separate `pty_type`, below. Pass every `.ptyAnswer` to `gatePluginRequest` and send exactly the bytes it returns to `surfaceId` as a keystroke, like a notification's Allow (the app presses only the fixed Allow/Deny keys, `macos/Sources/AnswerKey.swift`; a `.ptyType` is always pasted); it goes through `answer_permission`, so the key must be the live request of that very surface, not suspicious and not retired by typing, and it is consumed. Never write anything for a request it returns `nil` for. Every refused `.ptyAnswer` is queued for `takePluginRefusals()`, which the app drains after each batch and shows as a toast, "Refused <plugin id>: <reason>", in the core's fixed words, never the plugin's. A verified `permission_seen` carries the key as `request-key`, terminal-only requests included (answering one is refused).

**typing** (`pty_type`, its own consent line: "can type text into the current tab when you run one of its commands"; `pty_write` never implies it): `typing.type-text(text, enter)` works only while the plugin handles a palette item the user just chose or its key (`invokePaletteItem`), or a press or release of one of its own keys (`keyAction`), never from `on-event`, `init`, a row menu or anything else. It types into the tab that was selected when that call began, and only if `invokePaletteItem` (or `keyAction`) said that tab's terminal is on screen (no agents view or review screen over it). The text must be non-empty and at most 4096 bytes, with no escape (so no bracketed paste end `ESC[201~`), newline, CR or other control or invisible character except a tab; anything else is refused. The request becomes a `.ptyType`, and `gatePluginRequest` checks again at write time: the tab must still be selected, and must have no live permission request and no `hasUnresolved` prompt that may still be on screen. Its `PtyWrite` carries the text as `bytes`, written like any other with `ghostty_surface_text`, and `enter: true` when the command asked for Return, which the app then sends as a separate keystroke (Ghostty's `text:\r` action), never inside the paste. It shares the 10 per second limit with `pty.answer`.

**terminal** (`terminal_read`, red consent line "can read the text on any tab's screen when you use one of its commands or keys; this can contain secrets"): `terminal.read(surface, lines)` returns the last 1 to 50 visible lines of an open tab, oldest first, through `visible` and cut to 512 characters. Only during `run_user_action` (a palette command or key the user just used), any open tab, or during `on-hover-hold(true, surface)`, that surface alone; 8 reads each time, anything else refused. The app hands the core a `TabScreen` (`HauntCore.set_screen_reader`), which reads Ghostty's viewport on the main thread only and drops blank lines below the text; each read is logged.

**away** (`away`, consent line "can tell when you step away from your Mac (locked, asleep or idle) and come back"): the app's `Presence` reports every 5 s, and on screen lock, unlock, sleep and wake, whether the screen is locked or asleep and the seconds since the last input (`HauntPlugins.presence`). `PluginSet::presence` counts the user away when locked or idle for config.toml's `[presence] away_after` (minutes, 1 to 240, default 10) and calls `on-away-changed(true, 0)` once, then `on-away-changed(false, ms since the last input)` on return. Coming back is not a user gesture (they may be typing into another app right after unlocking), so a sheet the plugin shows in that call is held and shown on the next `HauntPlugins.appActivated()`, which the app calls when it becomes active; a card shows at once, and closing the sheet's id or going away again drops it.

**hold** (`notify_hold`, consent line "can hold Haunt's notifications for up to 4 hours, then show one summary (never a permission prompt's)"): `start(minutes)`, 1 to 240 (`HOLD_MAX_MINUTES`), holds Haunt's "turn finished" notes and other plugins' notifications; `release()` ends it. Several plugins may hold at once: the core keeps each holder's end (`CoreHandle::hold_notifications`), a second `start` moves only that plugin's end and clears its summary, and a release ends only the caller's hold. While holding, `set-summary(headline, actions)` gives the summary a plain headline (cut to 64) and at most 2 actions (labels plain, cut to 24, never a status word as for row labels); choosing one calls the holder's `on-action(id, "hold")`, which `notify_action` takes only for ids in that plugin's latest summary. Each start queues `HostRequest.holdNotifications(pluginId, minutes)`, each summary `holdSummary(pluginId, headline, actions)`, a release `releaseNotifications(pluginId)`; a disabled or unloaded plugin's hold ends. The app's `NotificationHold` keeps the held notes, ends each plugin's hold itself after its `minutes`, and when the last holder lets go posts one summary "held by <id>, <id> +n" whose body has the first two holders' "<id>: headline" lines, then the titles that waited, each plugin's prefixed with its id and shown through `visible` so none passes for Haunt's (a note taken back meanwhile, such as "done" for a tab that started again, leaves it); the first two holders' actions are its buttons. A note that an agent needs you is never held, and neither is a holder's own.

**top-row** (`sidebar_top`, consent line "can show one row of its own at the top of the sidebar"): `set(row)` puts one row above every sidebar group, drawn like a tab row (a hollow dot where the icon goes, the title, a right-hand text in `tone`, a sub line, an optional bar); `set(none)` takes it away. Text is plain: the title is cut to 32 characters (one with nothing visible is refused), the sub line to 48 and the right text to 24. The first plugin to set it owns it until it clears it or is disabled or unloaded; another plugin's `set` errs. It reaches the app as `SidebarSnapshot.top` (`TopRow`, with the plugin's id). With an `action`, a click calls `HauntPlugins.topRowClicked(pluginId:)`, which reaches the plugin as `on-action(action, "top")`.

**keys** (`keys`, consent line "can bind keyboard shortcuts of its own and tell when you press and release them"): `keys.bind(id, chord)` takes a chord with cmd, spelled as in `[keys]`, and returns an error for one that is malformed, lacks cmd, or is taken: the app reports every chord its key map uses or reserves with `HauntCore.setTakenChords` (canonical chord to owner, `"haunt"` for Haunt's and macOS's, else the `[keys]` name), before loading plugins and on every key map change. At most 8 per plugin. `bind` and `unbind` push `HostRequest.keysChanged`; the app then reads `HauntPlugins.keys()` (`PluginKey`, canonical chords) into the key map as `"<plugin id>/<id>"`, the same rules as a palette command's default key, so `[keys]` can move or drop one. `PluginKeys` (`macos/Sources/PluginKeys.swift`) watches key events before the menu and the terminal and calls `HauntPlugins.keyAction(pluginId:id:down:terminalShown:)` on a press and a release; lifting one of the chord's modifiers or the app resigning active counts as the release, and repeats are dropped. The plugin hears `on-action(id, "key-down")` and `on-action(id, "key-up")`, each able to type like a palette command. A disabled plugin's keys go. `keys.hover-hold("alt")` (none gives it up) takes the one hover-hold slot (`CoreHandle::claim_hover`; a second plugin is refused, a disabled one gives it up) and queues `keysChanged`; the app asks `PluginSet::hover_holder` who has it. The app's `HoverHold` watches without consuming anything: ⌥ alone, the pointer on a sidebar row and Haunt's window key with its sidebar showing, still true after 150 ms, call `hover_hold(plugin, true, row)`, which reaches the plugin as `on-hover-hold(true, row)`; letting go, another modifier, any key-down, leaving the row or losing key calls it with `false`, and ⌥ must come up before another start.

**exec** (`exec = [names]`, red consent line "can run <the commands> in your agents' project folders and read the output", plus "; gh acts with your GitHub login" for a gh command): `exec.run(surface, command)` starts one of six fixed, read-only commands (`plugin_exec::NAMES`; the WIT lists their exact arguments) and returns a job id at once; the outcome reaches the plugin as `on-exec(job, outcome)`. It runs in tab `surface`'s repository (`FsScope::tab_repo`): the project root of `opened_in`, the root `${cwd}` grants, never the tab's live cwd or an event's. It starts in that root with `GIT_WORK_TREE` and `GIT_DIR` (the root's `.git`, or the gitdir its `.git` file names) set, for gh as well, so git can't discover a repository nested inside it. It errs when there is no root. The binary comes from `/opt/homebrew/bin`, `/usr/local/bin` or the Command Line Tools or Xcode, never `PATH`, and only if it and every folder above it belong to root or the user and no one else can write to them (as `GitRunner.trusted`). The environment is cleared but for `HOME`, a fixed `PATH` and settings that stop prompts, colour and pagers (`GH_PAGER` too); system and global git config are off, attributes come from the empty tree, and `plugin_exec::SAFE_CONFIG`, the same list as the app's `GitRunner.safeConfig`, is pinned through `GIT_CONFIG_*` at command scope, which beats the repo's config and reaches every git gh starts: no fsmonitor, pager, hook, external diff, ssh, credential or signing program, no network, no submodules. `git log` also gets `--no-show-signature`, and `git status` gets `--ignore-submodules=dirty` (a submodule's own status would need a second git process; a moved gitlink is still reported) and is refused outright when the repo's config defines any filter driver. On macOS every command runs under `/usr/bin/sandbox-exec` (`plugin_exec::command`), whatever its file is called: git's profile denies `process-fork` and allows `process-exec` only of git's canonical path; gh's allows fork and exec only of gh's and git's canonical paths, and the git it starts inherits that profile. So nothing a repository names can start even if it appears between the filter check and the status, for instance through `.git/info/attributes`, which `GIT_ATTR_SOURCE` doesn't cover; if sandbox-exec is missing or reports a failure the command errs and git never runs unsandboxed. Apple has deprecated `sandbox-exec`: if a macOS release removes it, `exec`'s git commands and the review's working-tree diff stop working rather than run unsandboxed. Elsewhere (the Linux test build) git runs without it. The child leads its own process group: at 10 s the group is killed and `status` is -1; each stream is cut to 256 KB (`truncated`). At most 2 jobs per plugin run at once. `plugin_store::attach` registers the sink the job threads report to; a job finishes by locking the set, calling `on-exec`, and signalling `requests_queued` if the plugin asked for anything. A reloaded instance never hears the old one's jobs.

**notify actions**: choosing a plugin notification's action calls `HauntPlugins.notifyAction(pluginId:actionId:binding:)`, which reaches the plugin as `on-action(action-id, binding or "")`. The host takes only an (action, binding) pair from the plugin's last 64 notifications in this run. A binding that is an open tab's surface id brings that tab up, whether the user chose an action or the notification itself.

**0.5 draft, not linked yet**: the WIT also carries the shapes for the rest of 0.5, so plugins can build against them: `sound` (`sound`), `speech` (`speech`), `dock` (`dock`), `glow` (`glow`) and `title` (`title`). Every plugin implements `on-exec`, `on-away-changed` and `on-hover-hold`, empty if it doesn't use them. Until each lands, the host doesn't link the import and a manifest asking for its capability doesn't install; the limits in the WIT comments are the ones the host will enforce.

## Control socket and CLI

`<config_dir>/ctl` (`core/src/ctl.rs`) is bound by `start` next to `sock`, with the same directory, 0600, stale-socket and peer-uid rules, but separately, so hook floods and rate limits never reach it. At most 8 connections; each line must arrive whole within 5 s of the previous one and a connection is closed after 10 s; lines up to 64 KB. Each request is one JSON line and gets one JSON line back, `{"ok":false,"error":…}` on failure:

| request | response |
|---|---|
| `{"cmd":"dump"}` | `{"ok":true,"snapshot":<SidebarSnapshot>,"pending":[{"surface_id","key","tool","preview","suspicious"}],"decision_log_write_errors":n}` |
| `{"cmd":"event","line":<hook line, object or string>}` | `{"ok":true,"verified":bool,"changed":bool}`. The line goes through the same nonce check as `sock`: without the surface's nonce it is status-only. |
| `{"cmd":"decisions","query":"git","limit":50}` | `{"ok":true,"decisions":[<Decision>…]}`; `query`, `surface` (one surface id) and `limit` (default 50, at most 1000) are optional |

Nonces never appear in any response.

The `haunt` binary (`cli/`) talks to it: `haunt dump` prints the dump as pretty JSON, and `haunt decisions [query]` prints one decision per line as JSON, newest first. It uses `$HAUNT_CTL` if set, else `~/.haunt/ctl`.
